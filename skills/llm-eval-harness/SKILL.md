# LLM Eval Harness — metadata_extractor

## Verified state — two separate mechanisms, not one framework

There is no single "eval harness." There are two independent pieces that don't call each other:

### 1. Extraction → ground-truth diff (the actual accuracy check in use today)

- `notebooks/create_evaluation_dataset.py` runs the real `ServiceOrchestrator` (OpenAI-backed,
  key from AWS Secrets Manager) over PDFs in `data/original_articles/`, concurrently
  (semaphore-limited to 5), against a fixed schema (`title`, `authors`, `primary_product`,
  `indications`, `therapeutic_area` — constrained to a 6-value enum, `submission_date`,
  `acceptance_date`, `publication_date`). Output → `data/result_evaluation/llm_extracted_metadata.parquet`.
  This script does **not** produce `ground_truth.parquet` — that's assumed to already exist
  (hand-labeled), not generated here.
- `notebooks/metadata_extractor_results_evaluator.py` loads both parquet files, normalizes
  (accent stripping, dash normalization, list-vs-scalar handling), then scores:
  - **Exact match** on every shared column (NaN-vs-NaN counts as a match)
  - **Fuzzy match**, field-specific: `title`/`primary_product`/`indications`/`therapeutic_area`
    via tokenized Levenshtein similarity (`textdistance.levenshtein.normalized_distance`,
    inverted, tokenized with sklearn's `CountVectorizer` tokenizer); `authors` via Jaccard
    similarity on the name-set
  - Visualized as per-field histograms, closed with a written findings summary
- Both parquet files are DVC-tracked together under `data/result_evaluation.dvc` (2 files, ~32KB
  total as of last check) — get/push through DVC, don't hand-copy the parquet files.

### 2. `src/metadata_extractor/eval_utils.py` — a separate, more general retrieval/calibration library

Not called by the notebook above. Built for a different question: given embeddings or strings
for a set of queries and a set of references, find top-k matches
(`find_best_match_indices_in_reference[_batched]`), merge back to ground-truth IDs
(`merge_match_to_ref`, `merge_matches_to_query`), and produce **precision/recall/coverage
calibration curves per model or per scorer** (`get_binned_calibration_curve`,
`make_calibration_curves`, `get_precision_at_recall_or_coverage`). Semantic path uses cosine
similarity on embeddings; lexical path uses `rapidfuzz`/`process.cdist`. This is the piece built
for comparing multiple models/scorers against each other on a retrieval task (e.g. ontology
matching) — it is the right tool for a multi-model comparison, but it's currently unwired from
the ground-truth-diff notebook above.

## If asked to compare multiple LLMs (e.g. GPT-4o-mini vs 4.1-mini vs LLaMA)

This orchestration does not exist yet — building it means:

1. Parameterize `create_evaluation_dataset.py`'s `ServiceOrchestrator` call by model, and run it
   once per model → one `llm_extracted_metadata_<model>.parquet` per model, same schema.
2. For simple accuracy-vs-ground-truth comparison across models: extend
   `metadata_extractor_results_evaluator.py`'s `compare_llm_to_ground_truth()` to take a
   dict of `{model_name: results_df}` and produce one `comparison_df`/`comparison_df_fuzzy` pair
   per model, rather than assuming a single `results_df`.
3. For a retrieval/ranking-style comparison (which model more often surfaces the *correct*
   match, not just exact-string accuracy): this is what `eval_utils.py` is actually built for —
   feed each model's outputs in as a separate entry in the `query_embeddings_dict`/
   `scorer_dict` that `get_best_semantic_matches_per_model`/`get_best_lexical_matches_per_model`
   already accept, and use `make_calibration_curves` for the per-model comparison plot. This
   path gets you precision@recall tradeoffs per model, which raw exact/fuzzy-match accuracy
   doesn't.
4. Don't build a third, new comparison mechanism — extend one of the two above depending on
   whether the question is "does the extracted value match ground truth" (extend #2, the diff
   notebook) or "which model ranks the correct answer highest" (extend #1, `eval_utils.py`).

## Extending the ground-truth dataset

`ground_truth.parquet` is hand-labeled and not regenerated by any script here — adding
documents means manually labeling new rows with the same schema `create_evaluation_dataset.py`
extracts (see field list above), not running any existing "generate ground truth" tool, because
none exists. If asked to expand eval coverage, say this explicitly rather than assuming there's
an automated path.

## What this skill does NOT cover

The production metadata-extraction service itself (`ServiceOrchestrator`, prompt design,
`services/orchestrator.py`) — this skill is about evaluating extraction accuracy after the fact,
not about the extraction pipeline's implementation. Also doesn't cover the unrelated
`fdm-be`/`udp-celery` "evaluation_service.py"/"evaluator.py" — those are a product feature
(draft/refinement quality shown to end users), not this benchmarking harness; don't conflate
the two.
